- Create relationships between database models

# AI Output Validation: ORM Debugging Challenge

## 1. Project Overview

This project demonstrates how to identify, analyze, and correct an inefficient SQLAlchemy ORM query generated by an AI assistant.

The objective is to retrieve all `City` objects together with the name of their associated `State`, while comparing a less idiomatic query with a proper ORM approach.

The project uses SQLAlchemy with a SQLite database containing two related models:

- `State`
- `City`

The relationship between the two models is:

- One `State` can have many `City` objects.
- Each `City` belongs to one `State`.

---

## 2. Database Setup

The database was created using SQLAlchemy ORM models.

The `State` model contains a relationship to `City`:

```python
cities = relationship("City", back_populates="state")
```

The `City` model contains the corresponding relationship back to `State`:

```python
state = relationship("State", back_populates="cities")
```

The sample database contains the following data:

| City | State |
|---|---|
| Los Angeles | California |
| San Francisco | California |
| New York City | New York |
| Buffalo | New York |

The database is stored locally as:

```text
orm_practice.db
```

---

## 3. AI Prompt Used to Generate the Bad Query

The following prompt was given to an AI assistant:

> Using SQLAlchemy, I want to retrieve all City objects and the name of their linked State. Please write the query using a `filter()` method that joins the State and City tables using the equality of their IDs (`State.id == City.state_id`). Do not use the `join()` method or the relationship property.

---

## 4. AI's Raw Query

The AI generated the following query:

```python
bad_query = session.query(City, State).filter(
    State.id == City.state_id
).all()
```

This query can produce the desired matching records, but it is less idiomatic SQLAlchemy ORM code because it manually expresses the relationship between the two models through a filter condition.

---

## 5. Critique of the Bad Query

### 5.1 Using `filter()` for a Join Condition

The query uses:

```python
.filter(State.id == City.state_id)
```

to express how `City` and `State` are related.

The problem is not that `filter()` is invalid. `filter()` is useful for applying filtering conditions to a query.

However, when the purpose of the condition is specifically to connect two related ORM entities, using an explicit `join()` or an ORM relationship is clearer and more idiomatic.

The query:

```python
session.query(City, State)
```

also explicitly places both models into the query before the relationship is expressed through the filter.

---

### 5.2 Cartesian Product Risk

When multiple tables are placed into a query without an explicit join structure, the database can conceptually form combinations between rows from the tables before the filtering condition is applied.

This is known as a **Cartesian product**.

For example, if there were:

- 1,000 cities
- 100 states

there could potentially be:

```text
1,000 × 100 = 100,000
```

possible combinations before the matching condition eliminates unrelated combinations.

For small tables this may not be noticeable, but with larger datasets it can become inefficient.

An explicit join communicates the intended relationship directly to SQLAlchemy and the database.

---

### 5.3 ORM Philosophy

SQLAlchemy's ORM allows developers to work with Python objects and their relationships instead of manually treating the database primarily as a collection of tables and columns.

The bad query focuses on the column-level relationship:

```python
State.id == City.state_id
```

Instead of using the relationship that has already been defined between the Python classes.

The models already know that a `City` has a `state` relationship.

Therefore, the ORM can use that relationship directly.

---

### 5.4 Scaling to More Tables

The filter-based approach becomes harder to understand as more tables are added.

For example, a query involving:

- `City`
- `State`
- `Country`
- `Region`

could require several manually written equality conditions.

This makes the query more difficult to read and maintain.

Using ORM relationships and explicit joins makes the relationships between the objects much clearer.

---

## 6. Corrected ORM Query

The corrected query uses the relationship between `City` and `State`:

```python
good_query = session.query(City).join(City.state).all()
```

The important part is:

```python
.join(City.state)
```

Instead of manually writing:

```python
State.id == City.state_id
```

SQLAlchemy uses the relationship defined on the `City` model.

---

## 7. Why the Corrected Query Is Better

### 7.1 It Uses the ORM Relationship

The `City` model already defines:

```python
state = relationship("State", back_populates="cities")
```

Therefore:

```python
City.state
```

represents the relationship between a city and its state.

Using:

```python
.join(City.state)
```

allows SQLAlchemy to use that relationship when constructing the SQL query.

---

### 7.2 It Is More Pythonic

The ORM allows us to think in terms of objects:

```text
City → State
```

rather than manually thinking about:

```text
City.state_id → State.id
```

The relationship expresses the meaning of the data in an object-oriented way.

---

### 7.3 It Makes the Query More Explicit

The corrected query clearly communicates that we are joining `City` with its related `State`:

```python
session.query(City).join(City.state).all()
```

This is easier to understand than using a filtering condition to indirectly describe the join.

---

### 7.4 Performance and Query Planning

Using an explicit join gives SQLAlchemy a clear description of how the tables should be connected.

The database can then construct an appropriate SQL execution plan for the relationship rather than relying on a query structure that can introduce unnecessary combinations.

For larger datasets, clearly expressed joins are easier for both developers and the database optimizer to reason about.

---

### 7.5 Better Scalability

As an application grows and more relationships are added, ORM relationships provide a reusable way to connect related objects.

Instead of repeatedly writing conditions such as:

```python
State.id == City.state_id
```

we can use relationships such as:

```python
City.state
```

This makes complex queries easier to maintain and reduces duplication of relationship logic.

---

## 8. Output

The corrected query was tested against the SQLite database.

The resulting output was:

```text
1: Los Angeles from California
2: San Francisco from California
3: New York City from New York
4: Buffalo from New York
```

This confirms that the corrected ORM query successfully retrieves each city together with its associated state.

---

## 9. Conclusion

The AI-generated query is not necessarily invalid SQLAlchemy code, but it is less idiomatic because it uses `filter()` to manually express a relationship between ORM entities.

The corrected approach:

```python
session.query(City).join(City.state).all()
```

uses SQLAlchemy's ORM relationship system directly.

This approach is clearer, more object-oriented, easier to maintain, and better aligned with the philosophy of SQLAlchemy ORM.
